# Обновление инстанса ВУЗа (офлайн)

Этот документ — про **обновление уже работающего** инстанса, без потери данных.
Первичная установка — в [INSTALL_OFFLINE.md](INSTALL_OFFLINE.md).

## Главное правило

Обновление = **новый bundle + `install.sh --update`**. Инстанс **не сносится и не ставится заново**.
БД (`/var/library/pg-data`) и файлы книг (`/var/library/files`) живут в volume'ах и переживают
любое обновление. Удаление с потерей данных происходит только при `uninstall.sh --purge` — его при
обновлении запускать НЕ нужно.

## Как устроена версионность

- Единый источник правды — файл `VERSION` в корне репозитория (например `1.1.0`).
- При сборке bundle (`make-offline-bundle.sh`) эта версия:
  - становится тегом docker-образов (`library-api:1.1.0`, `library-frontend:1.1.0`) — **не `latest`**;
  - зашивается внутрь образов (Go-бинарник и Nuxt);
  - кладётся в bundle отдельным файлом `VERSION` и в имя архива.
- На сервере версию видно в двух местах:
  - `GET /api/health` → `{"status":"ok","version":"1.1.0", ...}`;
  - подвал админки (под блоком пользователя).
- `install.sh` при установке/обновлении сам прописывает `TAG=<версия>` в `.env`, поэтому
  `docker compose` всегда поднимает образы именно этой версии.

## Цикл выпуска новой версии (на машине разработчика)

1. Внести изменения в код.
2. Поднять версию в файле `VERSION` (по semver) и описать изменения в `CHANGELOG.md`.
3. (Опционально) пометить релиз в git: `git tag v1.1.0 && git push origin v1.1.0`.
4. Собрать bundle:
   ```bash
   ./deploy/scripts/make-offline-bundle.sh
   # → library-offline-bundle-1.1.0-YYYY-MM-DD.tar.gz
   ```
5. Передать архив на сервер института (USB/scp).

## Обновление (на сервере института)

```bash
# 1. Распаковать новый bundle
tar xzf library-offline-bundle-1.1.0-2026-08-01.tar.gz
cd library-offline-bundle-1.1.0-2026-08-01

# 2. Перенести существующий .env (там пароль БД и JWT-секрет — их нельзя терять)
cp ~/library-offline-bundle-1.0.0-2026-05-13/.env ./

# 3. Запустить обновление
sudo ./scripts/install.sh --update
```

Что делает `--update`:
- `docker load` новых образов из `images.tar`;
- синхронизирует `TAG` в `.env` с версией bundle;
- `docker compose up -d --force-recreate api frontend nginx` — пересоздаёт контейнеры на новых образах;
- api при старте сам накатывает недостающие миграции БД (`schema_migrations` помнит применённые — повторно не выполнит).

## Проверка, что обновление применилось

```bash
curl -s http://127.0.0.1/api/health
# Версия должна совпасть с версией нового bundle:
# {"status":"ok","version":"1.1.0","db":"connected"}
```

Та же версия должна отображаться в подвале админки. Если совпало — готово.

## Если фичи не применились

Симптом: обновили, но новых возможностей нет / `/api/health` показывает старую версию.

Проверь по порядку:

1. **Запускали `restart` вместо `--update`?** `docker compose restart` перезапускает контейнер
   на **старом** образе. Всегда используй `sudo ./scripts/install.sh --update`.
2. **Образы реально загрузились?**
   ```bash
   docker images | grep library-
   # Должны быть теги новой версии, напр. library-api  1.1.0
   ```
   Если новой версии нет — в bundle не было `images.tar` или `docker load` не отработал.
3. **`TAG` в `.env` соответствует новой версии?**
   ```bash
   grep '^TAG=' .env        # должно быть TAG=1.1.0
   ```
4. **api поднялся без ошибок миграций?**
   ```bash
   docker compose -f docker-compose.prod.yml --env-file .env logs api | tail -50
   ```
   Ищи `migrations applied`. Если миграция упала — api не стартует, фичи с новыми
   колонками БД работать не будут.
5. **Кэш браузера / nginx.** Обнови страницу с `Ctrl+Shift+R`; при необходимости
   `docker compose ... restart nginx`.

Корень почти всегда — пункт 1 или 2: контейнеры остались на старом образе. Версия в
`/api/health` — самый быстрый способ это увидеть.

## Откат на предыдущую версию

Старые образы остаются в docker после `docker load` новых. Чтобы откатиться:

```bash
# Вернуть прежний тег в .env
sed -i 's|^TAG=.*|TAG=1.0.0|' .env
docker compose -f docker-compose.prod.yml --env-file .env up -d --force-recreate api frontend nginx
```

⚠️ Откат образов **не откатывает миграции БД**. Если новая версия добавила колонки —
старый код их просто игнорирует и продолжает работать. Если же миграция была несовместимой
(MAJOR-релиз), перед откатом восстанови БД из бэкапа (`./scripts/restore.sh`).
